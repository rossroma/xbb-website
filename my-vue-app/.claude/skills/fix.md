# /fix — Bug 修复流程

## 自动触发条件

当用户输入包含以下特征时，自动调用此 Skill，无需用户显式输入 `/fix`：

- 报告 Bug、功能异常、错误
- 反馈不符合预期、不工作
- 关键词：「bug」「报错」「异常」「不对」「修一下」「有问题」「不工作」「坏了」「出错」

## 流程

### Phase 1：复现确认

**目标**：理解 Bug 现象，验证是否可复现

1. 收集：用户描述、浏览器控制台错误、网络请求状态
2. 可复现 → 构造最小复现用例；不可复现 → 分析日志追踪链路
3. 检查最近代码变更：`git log --oneline -10`

### Phase 2：根因分析

**目标**：定位 Bug 的根因代码

1. 追踪触发路径（组件渲染链路、数据流、API 调用）
2. 分析影响范围
3. 输出：根因定位（文件:行号）、触发条件、影响范围

### Phase 3：修复方案

**目标**：设计修复方案，评估副作用

1. 最小化修改原则：只改必要的代码
2. 评估是否影响其他模块
3. 用户确认方案

**🚫 铁律 #1：方案确认后方可修改代码**

### Phase 4：实施修复

**目标**：修复代码 + 必要时添加注释说明原因

### Phase 5：回归验证

**目标**：确保修复有效且不引入新问题

1. 验证修复是否解决原始问题
2. 运行测试：

```bash
pnpm test:unit          # 单元测试
pnpm test:e2e           # E2E 测试（涉及路由/页面跳转时）
pnpm type-check         # TypeScript 类型检查
pnpm lint               # ESLint + oxlint 检查
```

**🚫 铁律 #2：测试必须全部通过**

### Phase 6：修复报告

**目标**：输出修复摘要

输出：根因摘要、修复方案、回归测试结果。如有流程问题，记录到 `.claude/memory/state-problem-log.md`。

### Phase 7：文档同步

**目标**：检查修复是否影响文档

**检查清单**：

- 修复涉及路由变更 → 检查 `README.md`、`architecture.md` 路由结构
- 修复涉及组件 API 变更 → 检查 `docs/UI_KIT_SPEC.md`、`DESIGN.md`
- 修复涉及配置变更 → 检查 `CLAUDE.md` 自动化验证章节

**🚫 铁律 #4：文档必须同步**

## 完成标准

- [ ] Bug 已复现或定位
- [ ] 根因已确认
- [ ] 修复方案已获用户确认
- [ ] 代码已修复
- [ ] 回归测试通过
- [ ] 文档已同步（如有）
- [ ] 修复报告已输出
- [ ] 流程问题已记录（如有）
